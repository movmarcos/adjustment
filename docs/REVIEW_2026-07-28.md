## CRITICAL

### C1. Replace-by-reference destroys the old adjustment, then always errors [verified]
`03_sp_submit_adjustment.sql:284-358`

The duplicate-`GLOBAL_REFERENCE` cleanup uses the ADJ_HEADER **UUID** (`ADJ_ID`)
against columns keyed by the **numeric** `DIMENSION_ADJ_ID`:

- `UPDATE DIMENSION.ADJUSTMENT ... WHERE ADJUSTMENT_ID = '<uuid>'` (line 321-325,
  **outside** any try/except) → Snowflake coerces the varchar to NUMBER → cast error
  → whole submission returns Error. But the old header was already soft-deleted as
  `'Replaced'` at line 312-318 — **old adjustment gone from active views, new
  adjustment never inserted, no rollback.**
- `DELETE FROM {adj_tbl} WHERE ADJUSTMENT_ID = '<uuid>'` (338-346) is inside
  `except: pass` — even if reached it silently removes nothing, so a replaced
  upload's fact rows would stay live → double count.

The Adjustments-page delete flow (`2_Adjustments.py:312-317`) shows the correct
pattern: resolve `DIMENSION_ADJ_ID` first, use it for dimension/fact deletes.

Additional design flaws in the same block:
- Cleanup runs **before** the new adjustment's fate is known and regardless of
  `initial_status`: a submission into a signed-off COB (`Rejected - SignedOff`) or
  one that later gets **rejected** in approval still destroys the old adjustment.
- No transaction anywhere in the proc (EXECUTE AS CALLER, autocommit).
- Dedup fires only for `adjustment_type == 'direct'`, not `'upload'` (03:289) —
  confirm intent.

### C2. Pipeline claim result ignored → concurrent runs double-process; failure handler can fail other runs' work [verified]
`05b_sp_run_pipeline.sql:171-259`, `05_sp_process_adjustment.sql:455-461`

The Pending→Running claim (05b:194-202) is a correct atomic CAS, but its affected-row
count is never read and step 4 dispatches from the **pre-claim** `TEMP_QUEUE`
snapshot. `SP_PROCESS_ADJUSTMENT` then processes **all** Running rows for the combo
with no ownership check. The scheduled task can't overlap itself
(`ALLOW_OVERLAPPING_EXECUTION=FALSE` default), but a manual call (both test harnesses
call `SP_RUN_PIPELINE` directly) racing the 1-minute task means: both enumerate the
same Pending row, one wins the claim, **both** still CALL SP_PROCESS, both read the
same Running rows → duplicate DIMENSION.ADJUSTMENT rows + duplicate fact deltas
(the Direct path never cleans these up — see C5). If the loser's call fails, its
handler (05b:250-259) marks **every** Running row in the combo Failed — including
rows the winner is successfully processing.

### C3. Zombie 'Running' rows are unrecoverable and freeze their overlap group [verified]
`05b:194-202` (claim), `05b:136-147` (blocking), `05c_sp_force_process.sql:49-53`

If the orchestrator dies after the claim (task timeout, warehouse kill, session loss),
rows stay `Running` forever: there is no stale-Running reaper, and
`SP_FORCE_PROCESS_ADJUSTMENT` explicitly refuses anything not Pending/Approved — the
escape hatch cannot rescue the exact stuck state it exists for. Every subsequent poll
re-blocks all overlapping Pending rows against the zombie, and `_unblock_resolved`
only releases when the blocker is no longer Running — one dead run freezes the whole
overlap group until someone hand-writes an UPDATE. Same failure class as the
historical stuck-Pending bug, moved one state to the right.

### C4. FRTBALL is broken at three levels [verified]
1. **Submit**: the Scaling form offers FRTBALL (`1_New_Adjustment.py:290-296`, shown
   with `include_frtball=True` at 586/599) but `ADJUSTMENTS_SETTINGS` has no FRTBALL
   seed row (`01_tables.sql:370-433`), so `SP_SUBMIT` scope validation
   (03:226-232) always returns "Scope 'FRTBALL' is not active or not configured."
2. **Pipeline**: if a FRTBALL row ever exists (e.g. seeded later), 05b claims it to
   Running (194-202) but dispatch filters to `real_in` (221-226) — a FRTBALL row with
   no sibling real-FRTB row at the same (action, COB) is never dispatched → stuck
   Running (C3 state) and blocks overlapping work.
3. **Process**: when siblings do exist, the three concurrent FRTB* calls each include
   FRTBALL rows (05:458-459); whichever commits first marks them Processed, and
   later-starting calls skip applying them to their fact table — application is a
   timing lottery. The failure path (05:1629-1633) omits FRTBALL → left Running.
   And since SP_PROCESS catches all exceptions and returns JSON, 05b's per-combo
   Failed handler for `('{pt}','FRTBALL')` is dead code.

### C5. Direct path: failed-run fact rows are never cleaned → double count on retry
`05_sp_process_adjustment.sql:582-585` (same pattern at 1027-1031 for Scale)

The "re-run" DELETE is keyed on the **freshly generated** dimension IDs from this
run — it can never match rows written by a prior failed run (old IDs). Scenario:
Direct run inserts fact rows, fails later (e.g. RECORD_COUNT update) → header Failed
with rows live in the fact adjustment table; user retries → new IDs, delete no-ops,
second full copy inserted → upload double-counted. Direct has no supersede step to
self-heal (Scale mostly does).

### C6. Entity Roll: only the first Running EROL is executed, all are marked Processed [verified]
`05:1228-1239, 1582-1597`

`adj_ids` collects every Running EntityRoll for (scope, COB); `er_row =
df_adj_er.collect()[0]` processes exactly one; then `update_header_status(session,
df_adj_er, ...)`, `log_status_history(adj_ids, ...)` and the RECORD_COUNT update
(`WHERE ADJ_ID IN ({adj_ids_str})`) flip **all** of them to Processed. Two approved
EROLs for different entities at the same COB in one poll → the second is silently
skipped yet reported Processed. Also: `collect()[0]` order is not guaranteed to match
`adj_ids[0]`/`dim_adj_map` ordering, so audit rows can attach to the wrong
adjustment; `prior_dim_id` (1242) is read and never used.

### C7. Silent partial failure in dimension-ID mapping → NULL ADJUSTMENT_ID fact rows marked Processed
`05:254-279` (callers 499-502, 665-668)

Per-adjustment readback failures are swallowed (print only); callers raise only if
the map is **entirely** empty. A partially mapped batch still writes fact rows with
`ADJUSTMENT_ID = NULL`, is excluded from delete/supersede/count logic, and is marked
Processed. Also the readback matches on `COBID+PROCESS_TYPE+USERNAME+CREATED_DATE`
with `ORDER BY ADJUSTMENT_ID DESC LIMIT 1` — two headers by the same user at the same
timestamp map to the same dimension ID, silently merging two adjustments.

### C8. Admin page has no authorization gate [verified]
`5_Admin.py` (whole page; approver form 310-333, sign-off 150-229)

Any app viewer can add themselves (or an accomplice) to `ADJ_APPROVERS`, deactivate
approvers, reopen a signed-off COB, or edit templates. The 4-eyes control on the
Approval Queue is only as strong as this unguarded page. Sign-off reopen is one click
with no confirmation. (Related depth issue: approval itself is a raw UPDATE on
ADJ_HEADER — the maker-checker rule exists only in the UI layer.)

## HIGH

### H1. SCD2 key-fix UPDATE rewrites unrelated adjustments' rows
`05:1051-1099` — the cross-COB roll key remap UPDATE matches any row in the fact
adjustment table with the same TRADE/INSTRUMENT keys + COBID, not just this batch's
rows (`AND tgt.ADJUSTMENT_ID IN ({dim_ids_str})` is missing). Earlier same-COB
adjustments on the same trade get their keys rewritten to source-COB SCD2 versions;
rows at positions the roll doesn't occupy survive with wrong keys → future supersede
misses them → stranded double-counting rows.

### H2. Cross-batch supersede never matches NULL key parts
`05:1125-1141` vs `05:282-286` — netting COALESCEs NULLs into the surrogate key, but
supersede uses raw `fa.{k} = cur.{k}` equality → NULL keys never supersede → original
+ A + B all live. Roll leg also inserts NULL for non-KEY columns missing from the
combined view (05:937-941), making those rows permanently un-supersedable. And
`fa.ADJUSTMENT_ID NOT IN (...)` never matches NULL ADJUSTMENT_ID rows (see C7).

### H3. Streamlit action buttons: wrong states, unreachable retry, false audit rows [verified]
`2_Adjustments.py:306-428`
- First branch consumes `"Failed"` → the designed **Retry** branch (line 408) is
  unreachable dead code. Users will delete-and-recreate or send a Failed adjustment
  to approval instead.
- **Delete** offered for **Processed** rows: one click, no confirmation, no status
  re-check, hard-deletes fact/summary rows with failures swallowed (`except: pass`)
  while reporting success — invisible reconciliation break. Contradicts the app's
  own docs ("never hard-deleted": 5_Admin.py:470, 6_Documentation.py:1379).
- **Submit for Approval** offered for Failed/**Processed** rows, UPDATE has no
  `AND RUN_STATUS = ...` guard, history INSERT hardcodes `OLD_STATUS 'Pending'` →
  false audit data; re-approving a Processed adjustment re-queues it → double
  application risk. Recall (389-407) has the same unguarded pattern.

### H4. Approve/Reject: rowcount never checked → false success + false audit trail
`3_Approval_Queue.py:309-356` — the UPDATE is correctly guarded by
`AND RUN_STATUS = 'Pending Approval'`, but the result is not checked; the history
INSERT and `st.success` run unconditionally. Stale-page reject after a concurrent
approve writes a false 'Rejected' audit row while the adjustment processes.

### H5. Sign-off gate redesign lost upstream feed + entity granularity (spec FR5.1-5.4)
- New `ADJ_SIGNOFF_STATUS` (PK COBID+PROCESS_TYPE) is manually maintained on the
  Admin page; `BATCH.PUBLISH_VAR_SIGNOFF_STATUS` / `PUBLISH_SIGNOFF_STATUS_EXCEPTION`

- Sign-off is checked at submit only; pipeline/retry/approval re-queue paths never

### H6. Recurring adjustments: UI promises, backend absent [verified]
`1_New_Adjustment.py:157-159, 743-747, 795-807` collects and sends
`recurring_start/end_cobid`; `03_sp_submit` drops them (not in col_map, nothing

INSTANTIATE_RECURRING_TASK (every 5 min)". A RECURRING submission silently becomes a

### H7. Direct adjustments never rebuild the summary table (spec FR3.7/NF9)
`05:477-625` — the Direct branch touches only the detail table; Scale (1143-1158) and
EntityRoll (1532-1572) rebuild the summary. Every VaR/Stress/Sensitivity upload

### H8. VaR upload loses book/trade attribution; legacy REASON rule dropped

## Verified sound (coverage)

- **Roll semantics**: leg②(adjusted source × factor) + leg③(flatten target) nets to
  factor×adjusted(source); submit factor math (`-1` / `sf-1` / `sf`) and preview
  mirror it. Matches the agreed Scaling>Roll semantics.
- **FACT_TABLE_PK invariant**: Stress seed uses TRADE_CURRENCY; missing PK columns
  fail loudly at CTAS.
- **Within-batch netting**: DENSE_RANK keep-latest per (surrogate key,
  ADJUSTMENT_ID) with tie-free ordering.
- **EROL core**: code→ENTITY_KEY via DIMENSION.ENTITY with SCD2 multi-key support,
  hard fail on no-match; wipe+insert in explicit BEGIN/COMMIT/ROLLBACK; requires a
  distinct FACT_ADJUSTED_TABLE (raises otherwise).
- **Escaping**: user strings via `_esc`/`''`-doubling everywhere in 03/04/05/05b and
  pages 3/5; submit payload escaping order (backslash then quote) correct; numeric
  inputs int-coerced across pages 5/8/9.
- **Contracts**: every ADJUSTMENT_APP object referenced from Python exists in DDL,
  no typos; all INSERT/UPDATE column lists match name-for-name and count-for-count;
  all CALL signatures match; all DataFrame column accesses match SELECT case
  (sole miss = NEW_STATUS low above); preview column aliases match Python reads;
  status vocabulary consistent except 'Replaced'.
- **Category list**: ADJ_CATEGORY seed == verification.txt:477-495 exactly (19
  values); app reads IS_ACTIVE + SORT_ORDER.
- **Submit success allowlist** and failure-banner routing correct; widget-state
  versioning (`_k()`/reset_wizard) sound; no st.cache staleness (none used);
  Entity Roll and Direct-replace destructive confirmations gate Submit.
- **DDL redeploy**: tables/procs CREATE OR ALTER; stream drops intentional; DTs
  derived-only. (Destructive exceptions: seeds M7, task replace M6.)
- **Snowpark specifics checked**: `Row.__contains__` field-name check (04:79) valid
  (verified against snowflake-snowpark 1.53.1); `* EXCLUDE` + PARTITION BY valid;
  `dir()` guards valid.
